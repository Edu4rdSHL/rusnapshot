This release lets replicas be managed from rusnapshot itself: deleted at their target, and restored even when the snapshot they came from is no longer tracked on this machine.

## New

- `--del --from-replica` deletes a replica at its target instead of the local snapshot, which is left alone. The replica is remembered as deleted, the same as the ones removed by `keep`, so a snapshot still on this machine is not sent there again. The target is resolved as for a restore: looked up when a single one holds a replica, given as the value when several do.
- A replica recorded in the database but already gone from the target, for example deleted by hand, is removed from the database with a warning instead of failing.
- Deleting the newest replica is allowed. The next send uses the newest one left as its parent, and is full when none is.
- `--dry-run` covers `--del --from-replica`.

## Fixed

- `--restore --from-replica` looked `--id` up among the local snapshots, so it could only restore replicas of snapshots still tracked on this machine. Once `--clean` rotated a snapshot out, its replica stayed at the target but could not be restored, which is precisely the case remote retention exists for. `--id` is now looked up among the replicas, and without `--to` the restore goes to the source directory recorded with the replica.

## Compatibility

- No configuration or database change. Everything new happens with `--from-replica`.
- A restore from a target the database does not know about still works for snapshots tracked here, as in 0.9.0.
- `--from-replica` without `--restore` or `--del` is rejected.

## Internal

- 98 tests (48 unit, 50 end-to-end).
- Tested on a throwaway btrfs image covering restores of untracked snapshots, deletion with and without a local snapshot, replicas already gone from the target, several targets and dry runs, and against a server over ssh: 36 replicas deleted while keeping the newest one of each subvolume, with nothing sent again afterwards.
