This release adds restoring from a replica, so the second half of replication no longer has to be done by hand with `btrfs send` and `btrfs receive`.

## New

- `--restore --from-replica` brings a snapshot back from one of its replicas when it is no longer on this machine. The target is not given: replicas are recorded, so it is looked up. When several targets hold one, the error lists them and one is passed as the value (`--from-replica ssh://backup@nas/srv/backups/behemoth`), which also works for a target the database does not know about.
- The replica is received into `<dest_dir>/.restore/`, its identity is checked against the one at the target, and the restore is taken from it. The received copy is dropped afterwards: it shares its extents with the restore, so nothing is lost and no untracked subvolume is left behind.
- The `ssh_options` of the matching `[[replicate]]` section are reused, so a restore needs no extra configuration.
- Nothing is transferred when the snapshot is already here, when the restore target exists or when the replica is missing at the source; each case says what to do instead. `--dry-run` covers it.
- A replica sent with `exclude` does not contain the excluded paths, and neither will the restore. That is reported before and after, because a home restored this way is missing whatever the target left out.
- `--list` gives each table a heading, `SNAPSHOTS` and `REPLICAS`, replacing the plain `Replicas:` label.

## Fixed

- `--restore` without `--to` restored to the snapshots directory instead of the directory the snapshot was taken from whenever a configuration file was used. `dest_dir` is `--to` on the command line and the snapshots directory in the file, and the fallback to the recorded source was unreachable with `-c`, which is every documented flow. It only failed safely because that directory usually exists; with a `dest_dir` that does not, such as an unmounted backup disk, the restore landed there instead. The file value is now dropped for `--restore`, an explicit `--to` still wins and every other operation keeps it.
- The `+` at the line junctions of the `--list` tables are gone. The listings are wider than a terminal, so the rules wrapped at a different point than the rows they separate and the crosses ended up scattered across the screen.

## Compatibility

- No configuration, database or command line change. `--from-replica` is opt-in and nothing else behaves differently, except a `--restore` with `-c` and no `--to`, which now goes where it was documented to go.

## Internal

- 95 tests (48 unit, 47 end-to-end).
- The simulated `btrfs` used by the tests now sends a received subvolume under the identity it was received with, and materializes content on receive, so a replica round trip can be checked. Both gaps hid the real behaviour that the first implementation of the verification got wrong.
- Tested on a throwaway btrfs image and against a server over ssh: full send, the snapshot removed from the machine, the replica pulled back with the target resolved from the database, and the restored content checked with sha256 against the source.
