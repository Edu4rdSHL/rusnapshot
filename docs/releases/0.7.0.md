This release adds replication of snapshots to another disk or machine with `btrfs send`/`btrfs receive`.

## New

- `--send` replicates the read-only snapshots of the configured prefix and machine to one or more targets: a directory on a local btrfs filesystem (for example an external disk) or a directory on another host through ssh (`ssh://user@host:port/path`). Targets are defined in `[[replicate]]` sections of the configuration file, or given with `--target` on the command line.
- The first send of a subvolume is full; later ones are incremental from the newest replica of the same subvolume that exists on both sides. Replicas that disappeared from the target are detected and sent again.
- After each transfer the target filesystem is synced and the `Received UUID` of the replica is compared with the UUID of the source snapshot before the replica is recorded. A failed transfer is removed from the target and retried on the next run, and rusnapshot exits with a non-zero status.
- Replicas already present at the target but unknown to the database (for example after restoring the database) are adopted instead of sent again.
- `keep` per target: after sending, the replicas beyond the newest `keep` ones of each kind are deleted at the target. Pruned replicas are remembered so the local snapshots are not sent there again.
- `ssh_options` per target, for the key and known_hosts file to use when rusnapshot runs as root.
- `--dry-run` also covers `--send`: it prints what would be sent and pruned without contacting the target.
- `--list` shows the replicas present at each target below the snapshots table.
- Progress on stderr while sending when it is a terminal, and a summary line with size, time and speed for every send.

## Requirements for ssh targets

- `btrfs-progs` at the target and a target directory that already exists on a btrfs filesystem (rusnapshot does not create it).
- Key based authentication that works non-interactively (`BatchMode=yes` is always set).
- Passwordless sudo for the ssh user: the `btrfs` commands at the target run as `sudo -n btrfs ...`. A sudoers rule limited to `/usr/bin/btrfs` is enough. Logging in as root works too.

See the Replication section of `docs/SETUP_AND_USAGE.md` for the configuration and the systemd unit lines.

## Compatibility

- The database gets a new `replicas` table on the first run; the `snapshots` table is unchanged. Existing configuration files and units keep working, `--send` is opt-in.

## Internal

- 80 tests (40 unit, 40 end-to-end). The simulated `btrfs` used by the tests now covers `subvolume show`, `send`, `receive` and `filesystem sync`, and `ssh` and `sudo` are simulated too, so the replication tests need no root, no btrfs filesystem and no network.
- Tested against a server over ssh (Ubuntu 24.04, btrfs-progs 6.6.3, loop-mounted btrfs image) and against a USB disk formatted as btrfs: full and incremental sends, adoption, loss of the parent at the target, remote retention, unmounted target, and data integrity checked with sha256 on every side.
