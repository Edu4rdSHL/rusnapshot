This release fixes replication to targets with `exclude` when something under an excluded path carries the immutable or append-only attribute.

## Fixed

- `--send` failed with `Operation not permitted` while building the filtered copy when a file or directory under an excluded path had the immutable (`chattr +i`) or append-only (`chattr +a`) attribute. Those entries can't be unlinked, not even by root, and snapshots inherit the attribute, so a single such file was enough to stop the replication of a target: it aborts at the first snapshot that fails, leaving every later one unsent until the offending snapshot rotated out.
- The attribute is now cleared inside the filtered copy and the entry removed, with a warning naming each path that carried one. An immutable directory is covered too: it stops the removal of the ordinary files it holds, so the attribute is cleared from the directory rather than from the file that could not go away.

## Safety

- Attributes are only ever cleared inside the filtered copy, a throwaway read-write subvolume under `<dest_dir>/.staging/`. The snapshot it was made from is read-only and the live filesystem is never reached, so a file protected with `chattr +i` keeps its attribute everywhere it matters.
- The fast path is unchanged: the standard library's `remove_dir_all` handles every ordinary tree and the walk that clears attributes runs only after a removal was refused, so an exclude list without such files costs exactly what it did before.
- That walk takes the entry type from `symlink_metadata` and so removes symlinks as links instead of descending through them, and the attributes are read and written through a descriptor opened with `O_NOFOLLOW`.

## Compatibility

- No configuration, database or command line change. Targets without `exclude` behave exactly as in 0.8.0.

## Internal

- 93 tests (47 unit, 46 end-to-end), covering an immutable file under an excluded path, an immutable directory holding an ordinary file, and the refusal to follow a symlink while clearing attributes.
- Tested on a throwaway btrfs image with an immutable file, an append-only file, an immutable directory and symlinks pointing inside and outside the copy: full and incremental sends, the kept content checked with sha256 against the source, and the source snapshot verified to keep its attributes and stay read-only.
